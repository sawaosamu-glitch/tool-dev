| C1 | ローカルファースト個人用Webアプリ（Node.js+SQLite+ブラウザUI）の定番構成 | 個人・単一ユーザー・単一プロセス構成では「Node.js(Express) + better-sqlite3 + シンプルなREST/内部API + ブラウザフロント」が定番。better-sqlite3は同期API・高速・依存最小で「学習用途〜小規模アプリに最適」、逆に「高頻度同時書き込み」「TB級データ」には不向きと明記。フォルダ構成はcontrollers/models/routes/services/utils等のレイヤ分割（MVC的）が一般的だが、個人用の小規模アプリでは過剰分割せずシンプルな1プロセス構成で十分。なお「local-first」を厳密な意味（複数端末間の分散DB同期、CRDT等）で語る記事（Smashing Magazine）もあるが、これは端末間同期を伴うマルチデバイスアプリ向けの議論であり、本プロジェクト（1台のPC上でサーバーとDBが完結、ブラウザは単なるUI）には過剰。フロント/バックエンド分離は「必要だが軽量でよい」＝Express等で静的HTML/JSを配信しつつ同一プロセス内でSQLiteにアクセスする一体型構成が最も実用的。 | 2026-08-31 | [better-sqlite3 npm](https://www.npmjs.com/package/better-sqlite3) / [WiseLibs/better-sqlite3 GitHub](https://github.com/WiseLibs/better-sqlite3) / [Node.js SQLite Express チュートリアル](https://geshan.com.np/blog/2021/10/nodejs-sqlite/) / [Smashing Magazine: Local-First Web Development](https://www.smashingmagazine.com/2026/05/architecture-local-first-web-development/) | B | 「サーバー/クライアント分離してマルチデバイス同期を前提にした重厚なlocal-firstアーキテクチャ」は不要。Express（またはFastify等軽量フレームワーク）＋better-sqlite3の一体型・単一プロセス構成をMVP設計の基本方針として採用してよい。 |
| C2 | SQLite FTS5 vs ベクトル検索（embedding）、数百〜数千件規模の個人メモではどちらが実用的か | 複数の技術ブログ・比較記事で一致する見解：FTS5は「完全一致・専門用語・固有名詞の検索」に強く、セットアップが軽量（追加依存なし、ミリ秒未満のBM25ランキング）。ベクトル検索は「曖昧な言い回し・概念的な検索」に強いが、embeddingモデルの用意・計算コスト・追加ライブラリ（sqlite-vec等）が必要になる。データ規模については「数十万件規模までSQLiteで十分実用的」との記述があり、数百〜数千件の個人メモ規模ではFTS5単体でも十分実用に耐える。両者を組み合わせるハイブリッド検索（RRF: Reciprocal Rank Fusion）が理想論として推奨されているが、別記事（alexgarcia.xyz）では「基本的なデータセットではハイブリッドの複雑さは不要、まずはシンプルなFTS5で十分」と明言。個人メモ用途では「完全無料・ローカル完結」の制約とも整合し、embeddingを使う場合もローカルモデル（無料）が前提となるため実装難度が上がる。 | 2026-08-31 | [Why SQLite+FTS5 beats Vector DBs for AI Agent Memory](https://dev.to/fex_beck_27bfd4dccd05f062/why-sqlitefts5-beats-vector-dbs-for-ai-agent-memory-4inj) / [Hybrid full-text search and vector search with SQLite (Alex Garcia)](https://alexgarcia.xyz/blog/2024/sqlite-vec-hybrid-search/index.html) / [Hybrid Search FTS5+Vector+RRF](https://ceaksan.com/en/hybrid-search-fts5-vector-rrf) / [asg017/sqlite-vss GitHub](https://github.com/asg017/sqlite-vss) | B | MVPはFTS5単体（キーワード検索）で開始するのが妥当。数千件規模なら性能面の懸念はない。ベクトル検索・ハイブリッドはV2以降の拡張候補（「概念的な検索がしたい」というニーズが実際に出てから追加）とし、初期実装の複雑度・依存を最小化する。 |
| C3 | RAGでハルシネーションを抑える設計パターン（出典表示、根拠なき回答の拒否など） | 一致した知見：(1) システムプロンプトで「提供されたコンテキストのみを根拠に回答せよ。コンテキストに答えがない場合はその旨を明示せよ」という明示的な grounding 制約を与えることが有効（曖昧な「参考にしてね」的指示は不十分）。(2) 根拠不十分な場合は無理に答えず明示的に「わからない」と拒否する設計（Disciplined Refusal）が、医療AI等の高リスク領域でも標準的なベストプラクティスとして推奨されている。ある研究では拒否率を上げることでハルシネーション率が0.128→0.083に減少という定量結果も報告。(3) 出典（根拠となった元メモ）を回答に必ず併記させる「引用強制（citation-shaped answer）」もハルシネーション抑制と検証可能性向上に有効。ただし「引用があるからといって内容が正しいとは限らない（fake citation）」という指摘もあり、出典表示だけで安心せず、検索結果の関連度が低い場合はそもそも回答自体を控えるロジックが必要。 | 2026-08-31 | [Microsoft Learn: RAGのプロンプトエンジニアリング](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-prompt-engineering) / [RAG Grounding: 11 Tests That Expose Fake Citations](https://medium.com/@Nexumo_/rag-grounding-11-tests-that-expose-fake-citations-30d84140831a) / [Measuring and Enhancing Trustworthiness of LLMs in RAG (arXiv)](https://arxiv.org/pdf/2409.11242) | B（Microsoft Learn記事のみA相当、他はB） | QAアプリの回答生成プロンプトには「検索結果（=個人メモ）に書かれている内容のみを根拠に回答すること」「根拠が見つからない場合は『メモの中に関連情報が見つかりませんでした』と明示すること」という2点を必須要件としてSRSに反映する。回答には必ず参照元メモ（ID/タイトル/日付）を提示する仕様とする。 |
| C4 | ローカルSQLiteファイルのバックアップ・データ破損対策のベストプラクティス | SQLite公式ドキュメントによれば、WALモード（Write-Ahead Logging）は書き込み時のクラッシュ耐性向上・読み書き非ブロック化に有効で、個人用ローカルアプリでも標準的に有効化すべき設定。ただし(a) チェックポイント処理により定期的にWALファイルをメインDBに反映する必要があり長時間のトランザクションがあるとWALファイルが肥大化する可能性、(b) WALファイル・共有メモリファイルはメインDBファイルと必ずセットで管理する必要がある（分離するとデータ損失リスク）という注意点がある。バックアップについては、SQLite公式の`.backup`コマンド（ページ単位の完全コピー、書き込み中でも安全に実行可能）または単純な`cp`コマンドによるファイルコピーが「個人・単一ユーザー用途では最もシンプルで確実」と評価されている。破損防止の基本原則は「全ての書き込みをトランザクションで囲む」「WALモードを使う」「定期的にバックアップを取る」「ストレージのエラーを監視する」の4点に集約される。 | 2026-08-31 | [SQLite公式: Write-Ahead Logging](https://sqlite.org/wal.html) | [Backup strategies for SQLite in production (oldmoe.blog)](https://oldmoe.blog/2024/04/30/backup-strategies-for-sqlite-in-production/) / [SQLite Database Integrity Check](https://www.systoolsgroup.com/how-to/check-sqlite-database-for-corruption/) | A（sqlite.org公式）+ B（oldmoe.blog） | 実装方針として (1) `PRAGMA journal_mode=WAL;` を起動時に必ず設定 (2) アプリ起動時 or 定期タイマーでDBファイル＋WAL/SHMファイルをまとめて別ディレクトリへコピー（`.backup`コマンドまたは`cp`）する自動バックアップ機能をMVPスコープに含める (3) 「データ消失・破損は絶対避けたい」という要件に対する具体的な対策としてSRSに明記する。 |
| C5 | 「使い方がシンプルで続けやすい」個人用メモ・ナレッジアプリのUI/UX上の工夫 | 複数の記事・実例（Obsidian, Logseq等）で共通する知見：(1) 「キャプチャの摩擦（capture friction）」を徹底的に減らすことが継続利用の最大要因——「5秒以内にメモを書き始められないと習慣化しない」という指摘。(2) 分類・整理は最小限にする——「使い始めに必要なカテゴリは数個で十分。複雑な分類体系は逆に継続を妨げる」。(3) Logseqの「デイリーノート（journal）」方式は「どこに保存すべきか」という意思決定コストをゼロにする設計として高く評価されている——まず時系列に書く→後から整理、というcapture-first-organize-laterの流れ。(4) 継続を決めるのはツールの機能ではなく習慣そのもの、という指摘もあり、UI設計は「習慣化を阻害しない（＝毎回迷わせない）」ことを最優先すべき。 | 2026-08-31 | [Logseq vs Obsidian比較 (glukhov.org)](https://www.glukhov.org/knowledge-management/tools/obsidian-vs-logseq-comparison/) / [Personal Knowledge Base Guide (bit.ai)](https://blog.bit.ai/personal-knowledge-base/) / [Obsidian vs Logseq (openreplay blog)](https://blog.openreplay.com/obsidian-vs-logseq-note-taking-app/) | C | MVPのUIは「メモ入力欄を常に最前面に置き、保存先やタグ分類を必須にしない（後から自由に整理可能）」「起動したらすぐに入力・検索ができる1画面構成」を基本方針とする。デイリーノート的な時系列一覧＋全文検索の組み合わせが、個人開発の初期UXとして再現しやすく低コスト。 |

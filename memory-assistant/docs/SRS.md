## 1. はじめに

### 1.1 目的
自分で収集したテキストデータを蓄積・整理し、質問すると蓄積した知識をもとに関連情報を検索・提示する個人用の「相談役」アプリを提供する。情報の散逸により必要な知識を思い出せない・探し出せないという課題を解消する。

### 1.2 範囲
本SRSはV1（MVP）のスコープを定義する。画像データの蓄積・検索、複数端末同期、外部課金APIの利用はV1の対象外とする（詳細は5章フェーズ計画、research/scope_table.md参照）。

### 1.3 用語集

| 用語 | 定義 |
|---|---|
| メモ | ユーザーが登録するテキスト情報の最小単位（タイトル・本文・タグ・日時を持つ） |
| 検索ベースQA | 全文検索の結果（メモの抜粋）をそのまま提示する回答方式。生成AIを使わない既定機能 |
| 生成ベースQA | Ollamaで検索結果を根拠に要約回答を生成する付加機能（Ollama未導入時は無効） |
| 出典 | 回答の根拠となった元メモのID・タイトル・登録日時へのリンク |
| 根拠なき回答の拒否 | 検索結果が0件、または関連度が著しく低い場合に、生成AIに回答させず「見つかりませんでした」を返す設計 |

## 2. システム概要

個人のPC上でNode.js製のローカルWebサーバーが起動し、ブラウザからアクセスして使用する単一ユーザー向けアプリケーション。メモの登録・検索・質問応答をすべてローカルで完結させる。

```
[ブラウザUI] --HTTP(localhost)--> [Express サーバー] --SQL--> [SQLiteファイル(FTS5)]
                                          |
                                          +--HTTP(localhost:11434, 検出時のみ)--> [Ollama]
```

主要機能: メモ管理／全文検索／検索ベースQA／生成ベースQA（任意）／バックアップ・エクスポート

## 7. 機能要件

優先度はMoSCoW（Must/Should/Could/Won't）。全Must要件はEvidence ID・ACC-*・TC-*に接続する（詳細はrequirements_ledger.md参照）。

### FR-DATA-001: メモを新規登録する
- **優先度**: Must
- **Given**: 利用者がブラウザでアプリを開いている
- **When**: 利用者がタイトル（0〜200文字、空欄可）・本文（1〜50,000文字）・タグ（0個以上、カンマ区切り）を入力し「保存」を押す
- **Then**:
  - メモがSQLiteに永続化され、一意のメモID・登録日時（ISO 8601, ローカルTZ）が付与される
  - 保存後、メモ一覧の先頭に表示される
  - 保存と同時にFTS5インデックスが更新され、直後の検索で当該メモがヒットする
- **例外**:
  - 本文が空の場合、保存ボタンを無効化しエラーメッセージ「本文を入力してください」を表示する
  - 本文が50,000文字を超える場合、保存前にエラーメッセージを表示し保存しない

### FR-DATA-002: メモの一覧を時系列で表示する
- **優先度**: Must
- **Given**: メモが1件以上登録されている
- **When**: 利用者がトップ画面を開く
- **Then**: 登録日時の降順でメモのタイトル・本文冒頭100文字・タグ・登録日時が一覧表示される（1ページ50件、それ以上はページング）
- **例外**: メモが0件の場合、「まだメモがありません。最初のメモを登録しましょう」という空状態文言を表示する

### FR-DATA-003: メモを編集する
- **優先度**: Must
- **Given**: 編集対象のメモが存在する
- **When**: 利用者が一覧からメモを選択し内容を変更して「更新」を押す
- **Then**: メモの内容が更新され、更新日時が記録され、FTS5インデックスが再構築される
- **例外**: 本文を空にして更新しようとした場合、FR-DATA-001と同じバリデーションでエラー表示する

### FR-DATA-004: メモを削除する
- **優先度**: Must
- **Given**: 削除対象のメモが存在する
- **When**: 利用者が削除ボタンを押し、確認ダイアログで「削除する」を選択する
- **Then**: メモがSQLiteから削除され、FTS5インデックスからも同時に削除される。一覧・検索結果から即座に消える
- **例外**: 確認ダイアログで「キャンセル」を選択した場合、何も変更されない

### FR-DATA-005: タグでメモを絞り込む
- **優先度**: Should
- **Given**: 1件以上のメモにタグが付与されている
- **When**: 利用者が一覧画面でタグを選択する
- **Then**: 選択したタグを含むメモのみが一覧に表示される
- **例外**: 該当メモが0件の場合、「このタグのメモはありません」と表示する

### FR-SYS-001: メモを全文検索する
- **優先度**: Must
- **Given**: メモが1件以上登録されている
- **When**: 利用者が検索ボックスにキーワード（3文字以上）を入力する
- **Then**:
  - SQLite FTS5（trigramトークナイザー）による検索が実行され、関連度順（BM25スコア昇順＝一致度が高い順）に結果が一覧表示される
  - 検索結果には該当箇所のハイライト抜粋が表示される
  - 検索結果表示までの応答時間は500ミリ秒以内（NFR-PERF-001参照）
- **例外**:
  - 一致するメモが0件の場合、「該当するメモが見つかりませんでした」と表示する
  - 入力が1文字以下の場合、検索を実行せず「3文字以上入力してください」と案内表示する（trigramトークナイザーは3文字単位でインデックスするため、1〜2文字の入力は原理的に検索結果と一致しない（3文字未満のトリグラムを構成できないため）。research/v1_A_tools.md A4参照）

### FR-SYS-002: 質問に対する検索ベースQAを返す（既定機能）
- **優先度**: Must
- **Given**: メモが1件以上登録されている
- **When**: 利用者が質問入力欄に質問文を入力し「相談する」を押す
- **Then**:
  - 質問文から3文字以上の部分文字列（名詞候補・キーワード）を抽出し、FTS5のOR結合クエリとして検索を実行する（詳細な抽出アルゴリズムはSDD 1章SearchServiceインターフェース定義を参照）。関連度上位5件のメモ抜粋を出典（メモID・タイトル・登録日時へのリンク）付きで表示する
  - Ollamaが検出できない場合、または生成ベースQAが無効設定の場合は、常にこの検索ベースQAの結果のみを表示する
- **例外**: 検索結果が0件の場合、生成AIの有無に関わらず「関連するメモが見つかりませんでした」と表示し、それ以上の処理（生成AI呼び出し等）を行わない（FR-SYS-004参照）

### FR-SYS-003: Ollama検出時に生成ベースQAを返す（付加機能）
- **優先度**: Should
- **Given**: FR-SYS-002の検索結果が1件以上あり、かつ起動時にOllamaが検出されている
- **When**: 利用者が質問入力欄から「相談する」を押す
- **Then**:
  - 検索結果上位5件の抜粋のみをコンテキストとして設定ファイルで指定されたOllamaモデル（既定: qwen3:4b）に渡し、要約回答を生成する
  - システムプロンプトには「コンテキストに記載された内容のみを根拠に回答すること。コンテキストに答えがない場合は『分かりません』と回答すること」を固定文言として含める
  - 生成された回答には検索ベースQAと同じ出典一覧を併記する
  - 生成AI応答待機中はローディング表示を行い、10秒以内に応答がない場合はタイムアウトし検索ベースQAの結果にフォールバックする
- **例外**: Ollama呼び出しがエラーになった場合、エラーを利用者に通知せず検索ベースQAの結果のみを表示する（生成AIはあくまで付加機能のため、失敗してもアプリ全体の利用を妨げない）

### FR-SYS-004: 根拠なき回答を拒否する
- **優先度**: Must
- **Given**: 利用者が質問を送信した
- **When**: FTS5検索結果が0件、または検索結果の関連度が著しく低い（1件もタイトル・本文中に検索語の実質一致がない）場合
- **Then**: 生成AI（Ollama）を一切呼び出さず、「メモの中に関連情報が見つかりませんでした。別のキーワードで質問するか、まずメモを登録してください」というメッセージのみを表示する
- **例外**: なし（本要件が最優先で適用される）

### FR-DATA-006: メモをエクスポートする
- **優先度**: Should
- **Given**: メモが1件以上登録されている
- **When**: 利用者が「エクスポート」ボタンを押し、形式（Markdown一括ファイル／JSON）を選択する
- **Then**: 全メモを選択形式でファイル化し、ローカルの `exports/` ディレクトリに保存する。完了後、保存先パスを画面に表示する
- **例外**: メモが0件の場合、エクスポートボタンを無効化する

### FR-SYS-005: データを自動バックアップする
- **優先度**: Must
- **Given**: アプリが起動している
- **When**: (a) アプリ起動時 (b) 24時間ごと（設定変更可） (c) プロセス終了シグナル（SIGINT/SIGTERM）受信時
- **Then**: better-sqlite3の`backup()`APIを用いてSQLiteファイル全体を `backups/backup_[YYYYMMDDHHmmss].db` として複製する。直近7世代を保持し、それより古い世代は自動削除する
- **例外**: バックアップ先ディレクトリへの書き込みに失敗した場合、コンソールにエラーログを出力し、アプリ本体の動作は継続する。ただし連続2回失敗した場合はUIに警告バナーを表示し、利用者がディスク容量不足等に気づけるようにする（黙って失敗し続けることを防ぐ。Codex役レビュー指摘C-008対応）

### FR-EXT-001: Ollamaの有無を検出する
- **優先度**: Must
- **Given**: アプリが起動する
- **When**: 起動処理の一部として `http://localhost:11434/api/tags` へヘルスチェックリクエストを送る
- **Then**: 200応答があれば「生成ベースQA利用可能」、それ以外（接続不可・タイムアウト等）は「検索ベースQAのみ」と画面に状態表示する。判定結果はセッション中キャッシュし、毎回の質問ごとに再チェックしない
- **例外**: ヘルスチェックが3秒以内に応答しない場合、Ollama未検出として扱う

### FR-ADM-001: 使用するOllamaモデルを設定する
- **優先度**: Could
- **Given**: 利用者が設定ファイル（`config.json`）を編集できる
- **When**: `ollamaModel` フィールドに任意のモデル名（例: `qwen3:8b`）を指定してアプリを再起動する
- **Then**: 以降の生成ベースQAは指定されたモデルを使用する
- **例外**: 指定モデルがOllama側に存在しない場合、FR-SYS-003のOllama呼び出しがエラーとなり、検索ベースQAにフォールバックする

### FR-UX-001: Ollama未検出時に導入ガイドへの導線を表示する
- **優先度**: Could
- **Given**: FR-EXT-001の判定結果が「検索ベースQAのみ」（Ollama未検出）である
- **When**: 利用者が質問入力欄付近の画面を見る
- **Then**: 「生成AIによる要約回答を使うには」という短いリンク/補足文言を表示し、クリックするとREADME.mdの「生成AIを使いたい場合（任意）」セクションの内容（Ollama導入手順の要約）をその場で表示する
- **例外**: Ollama検出時はこの文言を表示しない（Opus役レビュー指摘O-002対応。実装コストが低いためCould優先度で採用、Phase 6で時間があれば実装、なければV2に回してもDoDには影響しない）

### 対象外・Won't（V1）
- FR-WONT-001: 複数ユーザーでのログイン・権限管理（Won't。理由: 個人単一ユーザー用途のため不要）
- FR-WONT-002: 画像ファイルの登録・OCR・画像内容検索（Won't→V2 DEFER。理由: MVPスコープをテキストに絞るため）
- FR-WONT-003: クラウド同期・複数端末共有（Won't。理由: 「完全無料・ローカル完結」の制約と矛盾するため）

## 8. 画面・操作フロー

### 8.1 画面構成（単一ページアプリ、タブ切替なし）

```
┌─────────────────────────────────────────┐
│  [質問入力欄]              [相談する]    │  ← 常に最上部に固定
│  Ollama状態: ● 生成AI利用可 / ○ 検索のみ │
├─────────────────────────────────────────┤
│  [新規メモ入力: タイトル/本文/タグ] [保存]│
├─────────────────────────────────────────┤
│  [検索ボックス]  [タグ絞込 ▼]           │
├─────────────────────────────────────────┤
│  メモ一覧 / 検索結果 / QA回答（同一領域） │
│  各メモ: タイトル・抜粋・タグ・日時       │
│  [編集] [削除]                            │
└─────────────────────────────────────────┘
```

### 8.2 空状態文言

| 画面状態 | 文言 |
|---|---|
| メモ0件（初回起動） | 「まだメモがありません。最初のメモを登録しましょう」 |
| 検索結果0件 | 「該当するメモが見つかりませんでした」 |
| QA結果0件（根拠なし） | 「メモの中に関連情報が見つかりませんでした。別のキーワードで質問するか、まずメモを登録してください」 |
| タグ絞込結果0件 | 「このタグのメモはありません」 |

### 8.3 操作フロー（メモ登録→検索→質問）
1. 起動 → Ollama検出処理 → トップ画面表示（メモ一覧 or 空状態）
2. メモ入力欄にタイトル・本文・タグを入力 → 保存 → 一覧に即時反映
3. 検索ボックスにキーワード入力 → 関連度順に結果表示
4. 質問入力欄に質問文を入力 → 相談する → 検索ベースQA（＋Ollama検出時は生成ベースQA）を表示

### 8.4 入力バリデーション一覧

| フィールド | 必須 | 型・制約 | 違反時の挙動 |
|---|---|---|---|
| メモ タイトル | 任意 | 0〜200文字 | 200文字超は入力欄側で切り詰め、超過分は保存されない |
| メモ 本文 | 必須 | 1〜50,000文字 | 空はFR-DATA-001例外、50,000文字超は保存前エラー |
| メモ タグ | 任意 | カンマ区切り、1タグ最大30文字、最大20個 | 上限超過分は保存時に切り捨て、警告表示 |
| 検索キーワード | 必須 | 3〜1,000文字 | 1文字以下は検索を実行せず「3文字以上入力してください」と案内表示（FR-SYS-001例外） |
| 質問入力 | 必須 | 1〜1,000文字 | 空欄は「相談する」ボタンを無効化 |
| config.json ollamaModel | 任意 | 文字列（Ollamaのモデル名形式） | 不正値は起動時のOllamaヘルスチェックで実質的に「未検出」扱いになる |

### 8.5 異常系フロー

| # | シナリオ | システムの挙動 |
|---|---|---|
| 1 | メモ保存中にSQLite書き込みが失敗（ディスク容量不足等） | 保存失敗をエラーバナーで通知し、入力内容は画面上に保持（再送可能にする） |
| 2 | 検索実行中にFTS5クエリが不正な記号を含む | 特殊文字をエスケープしたうえで検索実行。エスケープ後も0件なら通常の0件表示 |
| 3 | 質問応答中にOllamaがタイムアウト（10秒超） | FR-SYS-003の例外どおり検索ベースQAへ自動フォールバックし、利用者にはエラーを見せない |
| 4 | 起動時にDBファイルが破損（`PRAGMA integrity_check`失敗） | 起動を中断し、最新バックアップからの復元手順（11章参照）を画面に案内する |
| 5 | 質問応答で検索結果が1件以上あるが、質問語がどのメモのタイトル・本文にも実質的に一致しない（関連度が閾値未満） | FR-SYS-004どおりOllamaを呼び出さず拒否メッセージを表示する（0件時と同じ扱い。判定ロジックはSDD 1章QAService.ask()を参照） |
| 6 | バックアップが連続2回失敗する（ディスク容量不足等） | UIに警告バナー「バックアップに失敗しています。ディスクの空き容量を確認してください」を表示する（FR-SYS-005例外） |

## 9. データ要件

### 9.1 データモデル

```
notes（メモ本体）
  id            INTEGER PRIMARY KEY
  title         TEXT              -- 空文字許容
  body          TEXT NOT NULL     -- 1〜50000文字
  tags          TEXT              -- カンマ区切り文字列
  created_at    TEXT NOT NULL     -- ISO 8601
  updated_at    TEXT NOT NULL     -- ISO 8601

notes_fts（FTS5仮想テーブル、notesとcontent紐付け、trigramトークナイザー）
  title, body   -- notesと同期（トリガーで自動更新）
```

### 9.2 データライフサイクル
- 生成: FR-DATA-001（保存時）
- 更新: FR-DATA-003（編集時、updated_at更新）
- 削除: FR-DATA-004（物理削除、論理削除は採用しない。理由: 個人用途で復元要件がなく、シンプルさを優先）
- 永続化先: プロジェクト直下 `data/memory-assistant.db`（WALモード）
- バックアップ: `backups/` 配下に直近7世代（FR-SYS-005）
- エクスポート: `exports/` 配下にMarkdown/JSON（FR-DATA-006、読み取り専用の複製）

### 9.3 保存形式
SQLite単一ファイル（`data/memory-assistant.db` + `data/memory-assistant.db-wal` + `-shm`）。設定は`config.json`（JSON、Ollamaモデル名・ポート番号・バックアップ間隔を保持）。

### 9.4 データ整合性制約
- `notes.body`は空文字列を許容しない（DB制約 `CHECK(length(body) >= 1)`）
- `notes_fts`は`notes`へのINSERT/UPDATE/DELETE時にSQLトリガーで同期し、手動でのFTS5再構築を不要にする
- `created_at`/`updated_at`はアプリケーション側でISO 8601形式（`YYYY-MM-DDTHH:mm:ssZ`相当、ローカルTZオフセット付き）を生成しDBに渡す
- バックアップファイル（`backups/*.db`）とエクスポートファイル（`exports/*`）は読み取り専用の複製であり、アプリはこれらに対する書き込み・同期処理を行わない

## 11. セキュリティ・監査

| 項目 | 内容 |
|---|---|
| 認証・認可 | 実装しない。ローカル単一ユーザー・localhostバインドのみで外部公開しない前提のため（NFR-SEC-001と整合）。**補償コントロール**: サーバーは`127.0.0.1`にのみバインドし`0.0.0.0`では待ち受けない（外部端末からの接続を物理的に遮断する）ことをFR-EXT-001実装の必須条件とする |
| 秘密情報管理 | 外部APIキーを一切使用しないため該当なし |
| 監査ログ | メモの作成・更新・削除操作をアプリログ（`logs/app.log`）に記録する（Should）。記録項目: 操作種別(create/update/delete)・対象メモID・操作日時。個人利用のため操作者IDは記録しない |
| データ保護 | SQLiteファイルはローカルディスクに閉じる。暗号化は行わない（個人ローカル利用のためV1ではスコープ外、DEFER） |
| インシデント対応 | データ破損検知時（`PRAGMA integrity_check`失敗）は起動時にエラー表示し、以下の復元手順をREADMEに明記する：(1)アプリを終了する (2)`data/`フォルダの中にある`memory-assistant.db-wal`と`memory-assistant.db-shm`という2つのファイルがあれば削除する（WALモードで動作しているため、壊れた`.db`と一緒に残った古いWALファイルが復元を妨げることがある） (3)`backups/`フォルダの中から一番新しい日付のファイルを`data/memory-assistant.db`という名前でコピーする（既存の`memory-assistant.db`を上書き） (4)アプリを再起動し、正常にトップ画面が表示されることを確認する（データの整合性チェックはアプリが自動的に行う。エラーが出る場合は1つ前の日付のバックアップで(2)〜(4)を再度試す） |

## 14. リスク・変更管理

リスク一覧は `research/research_v2.md`「リスク一覧」および `docs/risk_register.md` を参照。

### 変更管理プロセス
1. 要件変更が発生した場合、該当FR/NFRの「変更履歴」に日付・変更内容を追記する
2. 変更が他の要件・設計・テストに影響する場合、`docs/requirements_ledger.md`の設計ID・テストIDを辿って影響先を洗い出し、該当行の状態を「要確認」にする
3. 影響先（SDD/TEST_PLAN/実装/テスト）を更新し、更新完了後に状態を「確定」へ戻す
4. Must要件の追加・削除は都度、意思決定の理由をPROGRESS.mdに記録する（承認者は社長本人、個人開発のため追加の承認フローはない）

### エスカレーション基準
- 技術的に実現不可能と判明した場合
- 「完全無料・ローカル完結」の制約を満たせないことが判明した場合
- スコープが当初のMVP範囲を大幅に超える場合

### リリース判定基準（Definition of Done）
V1を「完成」と判定するには、以下を全て満たすこと（PROGRESS.mdにチェックリストとして記録する）。
- [ ] 本人（社長）が、SRS/SDDの要旨（何ができるか／できないか／セットアップの負担／画像非対応であること）を確認し、Phase 6着手の承認を得ている（Opus役レビュー指摘O-001対応。承認前は「実装着手可、ただし本番データ投入・継続利用の判断は保留」の位置づけとする）
- [ ] 全Must要件（FR/NFR）が実装され、対応するACC-*・TC-*が全てPASS
- [ ] `docs/E2E_SCENARIOS.md`の全シナリオがPASS
- [ ] 単体テストカバレッジ80%以上（NFR-MAINT-001）
- [ ] `npm run lint` / `npm test` / `npm run build`（該当する場合）が全て緑
- [ ] RYGゲート判定がGreen（`harness/review-log.md`参照）
- [ ] README.mdに以下が具体的に記載済み: Node.js未導入環境からのセットアップ手順、Ollama導入手順（生成AIを使いたい場合のみ・任意であることの明記）、DB復元手順（WAL/SHMファイルの扱いを含む）、trigram全文検索の特性（まれに関連度の低い結果が混ざりうること）の平易な説明
- [ ] 1つでも未達の場合は「完了」と宣言しない（黄金ルール準拠）

# スペックドリフト検出 — memory-assistant

nagame-devの汎用手順（SD-01/02/03）をこのプロジェクトに適用する際の具体的なチェック項目。

## SD-01: 定期チェック（週1回、または大きな変更のたび）
- `docs/SRS.md`の全FR/NFRについて、対応する実装コード（`src/`配下）が存在し、要件の意図と合致しているか
- OUT OF SCOPE（画像機能・認証・クラウド同期等）が実装に紛れ込んでいないか（`research/scope_table.md`参照）
- `docs/SDD.md`のコンポーネント一覧（C-01〜C-09）と`src/`の実際のファイル構成が一致しているか
- `package.json`の依存パッケージが`express`・`better-sqlite3`以外に増えていないか（ADR-001の最小依存原則、増えた場合はADRに理由があるか確認）

## SD-02: 実装完了時の受入条件検証
`docs/acceptance_criteria.md`の全ACC-*を1件ずつ、対応するテストがPASSしているかを確認する。1件でもFAILなら「完了」と宣言しない（SRS 14章DoD参照）。

## SD-03: テスト変更時の改ざん検出
`git diff`で`tests/`配下の変更を確認し、以下を検出する。
- テストファイルの削除
- `.skip()`等による無効化
- assertion（期待値）の緩和（例: `assert.equal(count, 1)` → `assert.ok(true)`）
- カバレッジの5%以上の低下

検出時は`CONSTRAINTS.md` C-AI-002（テスト削除・改ざん禁止）に基づき、テストを元に戻し実装側を修正する。

## ドリフト対処の原則
仕様が正しく実装が間違っている → 実装を修正。実装が正しく仕様が古い → 人間の承認後にSRS/SDDを更新。判断がつかない場合は`PROGRESS.md`に記録し人間にエスカレーションする。
